# ADR-003: ストレージを `StorageBackend` Protocol で抽象化する

- **Status**: Accepted
- **Date**: 2026-07-29

## Context

ZIP 原本の保存先が必要になる。ローカル開発と `docker compose` ではホストのディレクトリで十分だが、本番想定は ECS Fargate である。Fargate のコンテナファイルシステムは **エフェメラル** であり、タスクが置き換わればファイルは消える。複数タスクにスケールした場合、あるタスクが受け取ったファイルを別のタスクが返せない。つまり本番では S3（または EFS）が必須になる。

一方で、今回のスコープに AWS へのデプロイは含まれない（Phase 3 は別途）。**今 S3 を実装すると、ローカル開発に LocalStack か MinIO が必要になり、「`docker compose up` 一発」という起動体験を壊す。**

したがって問いは「今は何を実装するか」ではなく「**将来 S3 に差し替えるときに、どこまでが変更範囲になるか**」である。ここを設計で先に閉じておく。

## Options Considered

### 案 A: サービス層から直接ファイル I/O を呼ぶ

`skill_service.py` の中で `Path(settings.STORAGE_DIR) / key` を組み立てて `open()` する。

**Pros**

- 最短距離。中間層がなく読みやすい

**Cons**

- S3 移行時に **ビジネスロジックの中を書き換える** ことになる。保存・取得・存在確認の呼び出しがサービス層に散らばっていれば、その全箇所が変更対象
- サービス層のテストに実ファイルシステムが必要になる。テストが遅く、後始末が要る
- 「ローカルパス」という概念がドメインに漏れ出す。S3 にはディレクトリがないので、後で辻褄が合わなくなる

**評価**: 複雑さ ◎ / コスト ◎ / 習熟度 ◎ だが、**変更範囲が読めない**

### 案 B: `StorageBackend` を Protocol（構造的部分型）で定義し、実装を DI する

```python
class StorageBackend(Protocol):
    def save(self, key: str, data: bytes) -> None: ...
    def open(self, key: str) -> BinaryIO: ...
    def exists(self, key: str) -> bool: ...
    def delete(self, key: str) -> None: ...
```

`LocalStorage`（`./storage/` 配下）を実装し、FastAPI の依存性注入でサービス層へ渡す。

**Pros**

- **S3 移行の変更範囲が `S3Storage` クラスの追加と DI の 1 行差し替えに閉じる**。この「変更範囲の見積もりが立つ」こと自体が価値
- サービス層のテストで、メモリ上の偽実装（dict に持つだけ）を差し込める
- キー体系を S3 互換（`skills/{skill_id}/v{version}.zip`）に最初から揃えておけば、データ移行は `aws s3 sync` 相当で済む
- Protocol は **ABC の継承を要求しない**（構造的部分型）ので、実装クラスが抽象基底クラスに縛られない。テスト用の偽実装も、同じシグネチャのクラスを書くだけで通る

**Cons**

- 間接層が 1 枚増える。「今は 1 実装しかないのに抽象化するのは YAGNI では」という批判はありうる
- 抽象のインターフェースを誤ると（例: ローカル前提の `get_path()` を生やす）、抽象化した意味がなくなる

**評価**: 複雑さ ○（薄い層 1 枚） / コスト ◎ / 習熟度 ◎

### 案 C: 最初から S3 互換（MinIO）で統一する

ローカルの compose にも MinIO を立て、`boto3` で統一する。

**Pros**

- 開発と本番のギャップがなくなる。「ローカルでは動いたのに」が起きにくい
- 抽象化そのものが不要になる

**Cons**

- compose にサービスが 1 つ増え、バケット初期化のブートストラップ処理も要る。起動体験と README の手順が重くなる
- `boto3` の認証情報をローカルにも用意する必要があり、初見の人が詰まりやすい
- 今回のスコープに AWS 接続は含まれないのに、AWS SDK 依存だけ先に背負う

**評価**: 複雑さ △ / コスト △ / 習熟度 △（ECS 初学者の段階で、学習対象を増やしすぎる）

### 案 D: ZIP を DB（PostgreSQL の bytea / Large Object）に格納する

**Pros**

- 保存先が DB に一本化され、バックアップとトランザクション整合が同時に取れる（メタデータとファイルが同時にコミットされる）

**Cons**

- バイナリで DB を膨らませるとバックアップ・レプリケーション・接続プールへの負荷が跳ね上がる。50MB × 件数がそのまま DB サイズ
- ダウンロードのたびに DB からストリーミングすることになり、DB がファイル配信のボトルネックになる
- 一般的に「ファイルはオブジェクトストレージ、DB にはキー」がセオリーで、そこから外れる合理的理由がない

**評価**: 却下（スケール特性が悪く、標準的な構成から外れる）

## Decision

**案 B（`StorageBackend` Protocol + `LocalStorage` 実装）を採用する。**

これは「今すぐ必要な抽象化」ではなく「**移行コストを見積もり可能にするための抽象化**」である。YAGNI の観点では議論の余地があるが、次の 2 点で正当化できる。

1. **本番が S3 になることは既定事項**であり、「起きるかどうか分からない将来」への投機ではない
2. 抽象の厚みが極めて薄い（4 メソッド・実装は数十行）。誤った抽象を作ったときの捨てるコストが小さい

抽象のインターフェース設計で守る原則:

- **ローカルファイルシステム固有の概念を漏らさない**。`get_path()` のようなメソッドは生やさない。S3 に対応物がないメソッドは、それだけで抽象を壊す
- **キーは S3 のキー体系に合わせる**: `skills/{skill_id}/v{version}.zip`。ローカル実装ではこれをそのままサブディレクトリとして解釈する
- **`open()` はストリームを返す**（`bytes` を返さない）。ダウンロード時に 50MB をメモリへ全載せせず、`StreamingResponse` へ流せるようにするため

### `LocalStorage` の実装上の注意

- キーに `..` が入っていれば書き込み先が `STORAGE_DIR` の外に出る。**キーは内部生成（UUID + 版番号）なので原理的に安全だが、防御的に `STORAGE_DIR` 配下であることを resolve 後に検証する**（ADR-002 と同じ思想。安全性を「呼び出し元が正しいこと」に依存させない）
- 親ディレクトリは `mkdir(parents=True, exist_ok=True)` で作る

## Consequences

- `storage/base.py` に Protocol、`storage/local.py` に `LocalStorage` を置く。`storage/s3.py` は将来の追加場所として空けておく（空ファイルは作らない）
- 保存先は環境変数 `STORAGE_DIR` で注入する。compose では `./storage` をバインドマウントし、コンテナを作り直してもアップロード済みファイルが残るようにする
- S3 移行時の作業は「`S3Storage` を書く」「DI を差し替える」「既存ファイルを `aws s3 sync` する」の 3 点。**サービス層・API 層・テストのいずれも変更不要** ——この見積もりが立つことが本 ADR の成果物
- ストレージ層の削除（`delete`）は現時点で API から呼ばれないが、Protocol には含める。将来の版削除・ロールバック時に必要で、後から Protocol を広げるより最初から定義しておくほうが実装漏れに気づきやすい
