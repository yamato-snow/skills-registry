# ADR-005: 一覧・詳細は Server Components、アップロードのみ Client Component

- **Status**: Accepted
- **Date**: 2026-07-29

## Context

Next.js 15 の App Router では、コンポーネントは既定で Server Component（SC）であり、`"use client"` を書いた時点で Client Component（CC）になる。**この境界をどこに引くかがフロントの設計判断の中心**で、後から動かすとデータ取得コードもエラーハンドリングも書き直しになる。

さらにコンテナ構成に固有の事情がある。`docker compose` では:

- **サーバ（Next.js のコンテナ）から見た API は `http://backend:8000`**（compose のサービス名で名前解決される内部 URL）
- **ブラウザから見た API は `http://localhost:8000`**（ホストにポート公開されている）

つまり **同じ API が、実行される場所によって URL が違う**。この事実を設計に織り込まないと、「SC では動くのにブラウザから叩くと名前解決に失敗する」という詰まり方をする。

画面は 3 つ:

| 画面 | 性質 |
|---|---|
| 一覧（`/`） | 検索クエリで絞り込んだ結果を表示。URL を共有したい |
| 詳細（`/skills/[id]`） | 読み取り専用。ファイルツリーと版履歴 |
| アップロード（`/upload`） | ドラッグ&ドロップ、選択中のファイル名表示、送信中の進捗、成否の表示 |

## Options Considered

### 案 A: 全部 Client Component（従来の SPA 的な書き方）

`"use client"` + `useEffect` / SWR でブラウザから API を叩く。

**Pros**

- Pages Router や Vite + React の経験がそのまま活きる。心理的な障壁が最も低い
- データ取得の URL が 1 つ（ブラウザ視点）で済み、上記の二重 URL 問題に悩まなくてよい

**Cons**

- **初回表示が遅い**。HTML → JS → fetch → 描画の 3 往復。一覧のようなただの読み取り画面でこれを払う理由がない
- ローディング状態・エラー状態を全画面で自前実装することになる
- API の URL が **ブラウザに露出する**ため、将来 API を内部ネットワークに閉じる構成が取れなくなる
- App Router を選んだ意味がほぼ消える（RSC の利点を一切使わない）

**評価**: 複雑さ ○ / コスト ○ / 習熟度 ◎ だが、**フレームワークの選択と噛み合わない**

### 案 B: 全部 Server Component

アップロードも Server Actions（`"use server"`）で処理する。

**Pros**

- クライアント JS がほぼゼロになる
- API URL がサーバ内に閉じる

**Cons**

- **ドラッグ&ドロップと進捗表示が作れない**。これらは本質的にブラウザ側の状態（ドラッグ中か、何%送ったか）を必要とし、サーバには持てない
- Server Actions を挟むと、ファイルの実体が「ブラウザ → Next.js サーバ → FastAPI」と 2 ホップする。50MB のファイルを Next.js のメモリに一度載せることになり、無駄な中継が生まれる
- FastAPI 側のバリデーションエラー（422 の日本語メッセージ）を、Server Action の戻り値経由で画面へ運ぶ配管が増える

**評価**: 複雑さ △ / コスト ○ / 習熟度 △。**要件（D&D・進捗）を満たせない**

### 案 C: 読み取りは SC、ユーザー操作の途中状態が要る箇所だけ CC（ハイブリッド）

- 一覧・詳細 → SC がサーバ内 URL で直接 fetch
- 検索フォーム → 一覧ページの中の小さな CC（入力状態が要るため）。送信すると `searchParams` を変えてサーバ側で再取得
- アップロード → ページごと CC。ブラウザから FastAPI へ直接 POST

**Pros**

- **判断基準が一言で言える**: 「ユーザー操作の途中状態（入力中・ドラッグ中・送信中）が必要な箇所だけ Client」。この基準は他の画面が増えても機械的に適用できる
- 読み取り画面は 1 往復で HTML が返る。ローディング状態の実装が不要
- アップロードはブラウザ → FastAPI の直接 POST になり、Next.js を経由しない（中継のメモリ消費と実装が消える）
- 検索結果が URL（`?q=...`）に載るので、共有・ブックマーク・ブラウザバックがそのまま動く

**Cons**

- **サーバ用 fetch とブラウザ用 fetch で URL が違う**という事実を、コード上で明示的に扱う必要がある
- 「なぜここは Client なのか」を知らない人が読むと境界が恣意的に見える（→ コードコメントで補う）

**評価**: 複雑さ ○ / コスト ◎ / 習熟度 ○

## Decision

**案 C（ハイブリッド）を採用する。境界の基準は「ユーザー操作の途中状態が必要かどうか」。**

この基準を採ると、各画面の帰属は自動的に決まる:

| 画面 / 部品 | 種別 | 理由 |
|---|---|---|
| 一覧ページ | SC | 表示するだけ。途中状態がない |
| 検索フォーム（一覧の子） | CC | 入力中の文字列という途中状態がある |
| 詳細ページ | SC | 表示するだけ |
| アップロードページ | CC | ドラッグ中・選択中・送信中の 3 つの途中状態がある |

### 二重 URL 問題の扱い

`lib/api.ts` に **サーバ用とブラウザ用の 2 系統を明示的に分けて** 置く。

```ts
// SC から呼ぶ: compose のネットワーク内で backend を名前解決する
const INTERNAL_API_URL = process.env.INTERNAL_API_URL ?? "http://backend:8000";

// CC から呼ぶ: ブラウザが解決できる URL。NEXT_PUBLIC_ 接頭辞でバンドルへ埋め込まれる
const PUBLIC_API_URL = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:8000";
```

- `NEXT_PUBLIC_` 接頭辞の有無が **そのまま「ブラウザに露出するか」の意味**を持つ。これは Next.js の規約であり、命名だけで用途が判別できる
- 関数名も `fetchSkillsFromServer()` / `uploadSkillFromBrowser()` のように、**どちら側から呼ぶ関数かが名前で分かる**ようにする。混同したときの症状（コンテナ内から `localhost:8000` を叩いて接続拒否、ブラウザから `backend:8000` を叩いて名前解決失敗）は原因が分かりにくいため、名前で予防する

### コードに残す判断コメント

`"use client"` を書いた各ファイルの冒頭に、**なぜ Client なのか** を 1〜2 行で書く。ADR を読まない人（あるいは半年後の自分）が、境界を勝手に動かさないための歯止めとする。

### キャッシュの扱い

App Router の `fetch` は既定でキャッシュされうる。レジストリの一覧・詳細は「アップロード直後に反映されること」が期待される画面なので、**`cache: "no-store"` を明示する**。プロトタイプの規模ではキャッシュによる性能上の利得がなく、「アップロードしたのに一覧に出ない」という混乱のほうがコストが高い。

## Consequences

- `app/page.tsx`（SC・一覧）、`app/skills/[id]/page.tsx`（SC・詳細）、`app/upload/page.tsx`（CC・アップロード）、`app/_components/SearchForm.tsx`（CC）という構成になる
- CORS 設定が **必要になる**。ブラウザが `localhost:3000` から `localhost:8000` へ直接 POST するため、FastAPI 側で CORSMiddleware に許可オリジンを設定する（許可オリジンは環境変数で注入）
- 本番（ECS）では 2 つの URL を環境変数で与える。ブラウザ用は ALB のパブリックな URL、サーバ用はサービスディスカバリの内部 URL。**この 2 変数構成がそのまま本番に持ち上がる**のが、compose で二重 URL を正面から扱っておく利点
- `next.config.ts` に `output: "standalone"` を設定し、Docker の runner ステージへ最小限のファイルだけコピーする（Dockerfile 側と対で意味を持つ設定なので、両方にコメントを書く）
- 検索は GET のフォーム送信 + `searchParams` で実装する。クライアント側で結果配列を保持しないので、状態の二重管理が発生しない
