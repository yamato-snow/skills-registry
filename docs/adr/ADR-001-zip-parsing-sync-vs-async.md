# ADR-001: ZIP 解析をリクエスト内で同期処理する

- **Status**: Accepted
- **Date**: 2026-07-29

## Context

Skills レジストリの中核となる操作は「Skills パッケージ（ZIP）のアップロード」である。1 リクエストで以下が発生する。

1. ZIP を受け取る（上限 50MB）
2. ZIP の構造を検査する（`SKILL.md` の存在、path traversal、symlink、展開後サイズ、ファイル数）
3. `SKILL.md` の YAML frontmatter を読み、`name` / `description` / `tags` を取り出す
4. ファイルツリーを組み立てる
5. ZIP 原本をストレージへ保存し、メタデータを DB に書く

この一連の処理を **リクエストの中で完結させる**か、**受付だけ返してバックグラウンドワーカーに投げる**かは、この先のアーキテクチャ（インフラ構成・運用の複雑さ・API の契約）を大きく左右する。ここで決めておかないと後から「非同期にすべきだった」と作り直しになる部分なので、最初に判断を固定する。

前提となる利用規模:

- 社内向けレジストリ。同時アップロードは多くて数件、1 日あたりの投稿も数十件程度を想定
- ZIP は Skills パッケージ（Markdown + 小さなスクリプト類）であり、実測で数十 KB〜数 MB。上限の 50MB は保険
- 実行環境は ECS Fargate（ステートレス・複数タスクにスケールしうる）を前提に設計する

計測の目安として、50MB の ZIP を in-memory で検査しても CPU 時間は 1 秒未満、実際の投稿サイズ（数 MB）なら数十 ms のオーダーに収まる。ネットワーク転送のほうが支配的になる。

## Options Considered

### 案 A: リクエスト内で同期処理する

`POST /skills` の中で検査・保存・DB 書き込みまで済ませ、成功なら 201、検証エラーなら 4xx を **その場で** 返す。

**Pros**

- API の契約が単純: レスポンスがそのまま結果。クライアントはポーリングもリトライも要らない
- エラーが即座に、具体的に返せる。「`SKILL.md` が見つかりません」をアップロード直後に画面へ出せる
- 障害モードが少ない。キューの詰まり・ワーカー死亡・ジョブ再実行時の冪等性といった問題が **そもそも発生しない**
- インフラが API + DB + ストレージだけで済む。ECS のタスク定義も 1 種類
- 状態遷移（pending → processing → ready / failed）を DB とフロントの両方に持たなくてよい

**Cons**

- 重い処理を足すと（ウイルススキャン、静的解析、大きな展開）リクエストが伸び、ALB / uvicorn のタイムアウトに当たる
- アップロードが集中すると API のワーカースレッドを占有し、他のエンドポイント（一覧・検索）の応答に影響しうる
- リトライしたいときはクライアントに再アップロードさせるしかない

**評価**: 複雑さ ◎（最小） / コスト ◎（追加インフラなし） / 習熟度 ◎（FastAPI の通常の書き方の範囲）

### 案 B: Celery + Redis（または RabbitMQ）でワーカー分離

`POST /skills` は ZIP を保存して `202 Accepted` とジョブ ID を返し、検査はワーカープロセスが行う。クライアントは `GET /skills/{id}` をポーリングして `status` を見る。

**Pros**

- 重い処理をいくら足しても API のレイテンシに影響しない
- ワーカーだけを独立してスケールできる
- 失敗ジョブの再実行・リトライ戦略をサーバ側に持てる

**Cons**

- ブローカー（Redis 等）とワーカーという **2 つの新しい稼働コンポーネント** が増える。ECS ならタスク定義も監視も 2 倍
- API に「まだ検査中」という状態が生まれ、DB スキーマ（status カラム）・フロント（ポーリング/スピナー）・エラー表示のすべてに波及する
- ジョブの冪等性、ワーカーが途中で死んだときの孤児レコード、デッドレターキューの扱いを設計しなければならない
- ローカル開発の `docker compose` にも Redis とワーカーが増え、「第三者が 5 分で起動できる」という本プロトタイプの目標に逆行する

**評価**: 複雑さ ✕（大） / コスト △（Redis + ワーカータスクの常時稼働費） / 習熟度 △（Celery の運用経験は浅い）

### 案 C: SQS + Lambda（マネージド非同期）

ZIP を S3 に置き、S3 イベント → SQS → Lambda で検査する。

**Pros**

- 自前のワーカーを常時起動しなくてよく、アイドル時のコストがほぼゼロ
- リトライ・DLQ がマネージドで手に入る

**Cons**

- 案 B の「非同期であること」に由来する複雑さ（状態管理・ポーリング）は全部そのまま残る
- さらに **AWS 依存が実装コードに食い込む**。ローカルの `docker compose` で再現するには LocalStack 等が必要で、開発体験が落ちる
- 検査ロジックが API と Lambda に分かれ、コードの置き場所とデプロイ経路が二重化する

**評価**: 複雑さ ✕（大・クラウド依存） / コスト ◎（従量） / 習熟度 ✕（ECS すら初学者の段階でサーバーレス併用は学習コストが高い）

### 案 D: FastAPI の `BackgroundTasks` で「なんちゃって非同期」

レスポンスを先に返し、同一プロセス内で検査を続ける。

**Pros**

- 追加インフラゼロで API のレスポンスだけ速くなる

**Cons**

- **同じプロセスで動くのでスケール特性は同期と変わらない**。API のリソースを食う点は解決しない
- それでいて「まだ処理中」という状態管理の複雑さだけは案 B と同じだけ背負う
- コンテナが停止・再配置されると処理が消える。ECS のローリングデプロイと相性が悪い

**評価**: 複雑さ △ / コスト ◎ / 習熟度 ◎ だが、**得られる利点がほぼない**（複雑さだけ増える中途半端な選択）

## Decision

**案 A（リクエスト内で同期処理）を採用する。**

決め手は「非同期化が解決する問題を、現在の規模ではまだ抱えていない」こと。想定処理時間が 1 秒未満である以上、非同期化で得られるのはレイテンシ改善ではなく **将来の重処理に対する備え** だけであり、その備えのために状態管理・ブローカー・ワーカー監視という恒久的な複雑さを、プロトタイプの段階から支払うのは割に合わない。

同期でも設計上の逃げ道は確保しておく:

- 検査ロジックは `services/zip_inspector.py` に **FastAPI 非依存の純粋関数群** として置く。入力は `bytes`、出力は検査結果のデータクラスで、HTTP もリクエストコンテキストも知らない
- これにより、後日ワーカーへ移す場合も **呼び出し元を差し替えるだけ** で済み、ロジックの書き直しは発生しない

## 移行基準（この判断を見直す条件）

以下のいずれかが観測されたら案 B / C を再検討する。ADR は「いつ覆すか」を書いておいて初めて役に立つ。

1. **処理時間がタイムアウトに接近**: p95 のアップロード処理時間が ALB / uvicorn のタイムアウトの 50% を超えたとき
2. **スループットの圧迫**: アップロードが原因で一覧・検索 API の p95 レイテンシが悪化したとき（＝アップロードが API ワーカーを占有し始めた証拠）
3. **重処理の追加**: ウイルススキャン、サンドボックスでの静的解析、LLM によるメタデータ抽出など、秒オーダーの処理を検査パイプラインに加えると決めたとき

## Consequences

- `POST /skills` は結果を同期で返す。検証エラーは 422 / 413 / 400 で **その場で** 具体的に伝える
- DB に `status`（pending/ready/failed）カラムを持たない。レコードが存在する＝検証済みで配布可能、という不変条件が成り立つ
- フロントのアップロード画面はポーリング不要。POST の応答だけで成否を確定できる
- `docker compose` の構成は db / backend / frontend の 3 サービスに収まる
- アップロードのリクエストサイズ上限（50MB）は、リバースプロキシ / ALB 側にも同じ値を設定する必要がある（同期で受け切る以上、経路上のどこかで切られると原因が分かりにくい）
