# ADR-007: `SKILL.md` の本文を DB に保存し、検索対象と詳細プレビューに使う

- **Status**: Accepted
- **Date**: 2026-07-29

## Context

2 つの要望が別々に出てきたが、原因は同じところにある。

1. **検索が本文に届かない** — `description` に書いていないことは探せない。「あの Webhook を叩くやつ」を思い出して探す（ADR-004 が主用途と定義した「既知アイテムの再発見」）とき、手がかりが本文にしかないことは普通に起きる
2. **中身が画面で見られない** — 詳細ページに出るのは名前・説明・ファイル構成・版履歴だけ。`SKILL.md` に何が書いてあるかを見るには、ZIP をダウンロードして展開するしかない

どちらも「`SKILL.md` の本文がシステムのどこにも残っていない」ことに由来する。現状、本文は `zip_inspector` が frontmatter を読むときにメモリへ載り、frontmatter を取り出したあと**捨てられている**。

制約:

- `SKILL.md` 単体には既に **1MB の上限**が強制されている（`max_skill_md_size`。ヘッダ値の偽装に備えた実読み出し上限）
- このレジストリは Skills を**実行しない**（ADR-002 のセキュリティ境界、恒久的）。本文はあくまで表示と検索の対象であって、解釈して動かすものではない

## Options Considered

### 案 1: 本文全文を DB に保存する

`skill_versions` に `skill_md_body TEXT` を足し、アップロード時に保存する。

**Pros**

- **追加の I/O がゼロ**。`zip_inspector` は検証のために `SKILL.md` を既にメモリへ読んでいるので、`SkillPackage` にフィールドを 1 つ足して渡すだけ
- **要望 1 と 2 が同じカラムで両方解決する**。検索対象化とプレビューが別々の仕組みにならない
- 1MB 上限が既に効いているので、`TEXT` カラムとして問題になるサイズにならない

**Cons**

- 一覧クエリが素朴だと最大 1MB × 件数を引く（→ `deferred` で回避。下記）
- 本文が版ごとに増えるぶん DB のサイズは増える。ただし ZIP 原本をストレージに丸ごと持っている現状に比べれば誤差

**評価**: 複雑さ ◎ / コスト ◎ / 習熟度 ◎

### 案 2: 検索用の抽出テキストだけを保存する

見出しや箇条書きから検索に効きそうな部分だけを抜き出して保存する。

**Pros**

- 保存量が減る

**Cons**

- **抽出パイプラインという新しい部品が増える**。「何を残し何を捨てるか」は正解のない調整項目で、外したときの症状（探しているものが出ない）は原因が分かりにくい
- 要望 2（プレビュー）を満たせない。結局どこかで ZIP から本文を読み直すことになる
- 1MB 上限の下では節約効果も乏しい。**複雑さだけ増えて得るものがない**

**評価**: 却下

### 案 3: 本文を検索対象にしない（プレビューもしない）

**Pros**

- 変更なし

**Cons**

- 要望 1 と 2 の両方が未解決のまま残る。「`description` に書いていないが本文には書いてある」は主用途でまさに起きるケースで、割り切りの根拠が立たない

**評価**: 却下

## Decision

**案 1 を採用する。** `skill_versions.skill_md_body`（`TEXT NOT NULL`）を追加し、アップロード時に保存する。

### 保存するのは「frontmatter を除いた本文」

`SKILL.md` の全文ではなく、frontmatter を切り落とした後ろだけを保存する。

frontmatter には `name` と `description` がそのまま書かれている。これを本文に含めたまま検索対象にすると、**「`name` に当たった Skill は本文にも当たったことになる」という常に真の判定**が混ざる。結果、[ADR-006](ADR-006-search-multi-token-relevance-snippet.md) の `matched_fields` は毎回 `body` を含み、スニペットは本文ではなくメタデータの再掲を表示する。ヒット箇所の可視化が意味をなさなくなるので、切り分けは保存の時点で行う。

失うものは無い。`name` / `description` / `tags` は構造化して別のカラムに持っている。

### 一覧クエリの重量化を防ぐ

`skill_md_body` は SQLAlchemy の **`deferred`** にする。既定では読まれず、必要な場所だけ `undefer` する。

| 経路 | 本文を読むか | 理由 |
|---|---|---|
| 一覧（`q` 無し） | 読まない | スコアリングもプレビューもしない |
| 一覧（`q` 有り） | 読む | Python 側のスコアリングとスニペット抽出に要る |
| 詳細 | 読む | プレビューに出す |
| ダウンロード | 読まない | ZIP を返すだけの処理で最大 1MB × 版数を読む理由がない |

最新版を畳む `DISTINCT ON` の subquery も、列を明示して組み立てる。`select(SkillVersion)` と書くと **`deferred` な列が SELECT 句から落ちて `WHERE` で参照できなくなる**ためで、同時に「本文が要らない一覧では列に入れない」ことも同じ仕組みで実現できる。

### 表示側の XSS 対策は「サニタイズ」ではなく「経路を作らない」

本文はアップロードした人が自由に書けるテキストで、そのまま HTML として解釈させれば当然 XSS になる。**ADR-002 と同じ考え方でこれを扱う**——攻撃を検知して落とすのではなく、攻撃が成立する経路を最初から作らない。

- 描画は `react-markdown` を **`rehype-raw` なし**で使う。この構成では本文中の生 HTML はパースされず**テキストノードとして扱われるのが既定の動作**で、`<script>alert(1)</script>` はそのまま文字として表示される
- `dangerouslySetInnerHTML` はこのプロジェクトのどこでも使わない。検索語のハイライトも「テキストを分割して React 要素として組み立てる」実装にしてあり、同じ理由で危険な経路が存在しない
- `react-markdown` の既定エクスポートは hooks を使わない同期コンポーネントなので、**Server Component のまま描画できる**（`MarkdownHooks` のほうは Client 専用）。ADR-005 の境界を動かさずに済む

## Consequences

- **スキーマが変わる**。`create_all` 運用（design.md §3）なので、既存の開発 DB には反映されない。フェーズ 2 の更新後は `docker compose down -v` が必要になる。README と `docs/manual-test.md` の冒頭に明記する
- Alembic はまだ入れない。design.md の導入基準は「**データを消せなくなった時点**」で、現在のデータはデモとシードのみ。むしろ今回、シードスクリプトを用意することで「消しても 1 コマンドで戻る」状態が強化されている
- `GET /skills/{id}` のレスポンスに `skill_md_body` が増える
- 本文が検索対象になったことで [ADR-006](ADR-006-search-multi-token-relevance-snippet.md) の 3 点セットが成立する。この 2 本は同時に決めないと片方だけでは意味をなさない
- **このレジストリが Skills を実行しないという境界（ADR-002）は変わらない。** 本文は表示と検索の対象であって、解釈して動かすものではない
