# ADR-008: 入力検証の上限値と UTF-8 要件 — 何を守っているかを再導出し、値を実測で定める

- **Status**: Accepted
- **Date**: 2026-07-30
- **Amends**: [ADR-002](ADR-002-zip-security-in-memory-inspection.md)（in-memory 検査という Decision は不変。検証項目の上限値の根拠を再導出し、`MAX_FILES` の既定を変更する）

## Context

### この ADR が必要になった経緯

フェーズ 2 完了後、「**アップロードを失敗させる要件の根拠を示すドキュメントはあるか**」という問いが出た。棚卸しの結果、根拠が書かれていない箇所が 3 か所あった。

| 検証項目 | 状態 |
|---|---|
| No.09 ファイル数上限（既定 500 件） | 上限を設ける理由は ADR-002 にあるが、**なぜ 500 かの導出がない** |
| No.14 UTF-8 必須 | **判断として記録されていない**（実装にだけ存在する） |
| No.15 `SKILL.md` 単体上限（1MB） | 二重チェックの必要性は ADR-002 にあるが、**なぜ 1MB かの導出がない** |

加えて記載漏れが 1 件。`docs/design.md` §7 の環境変数表に `MAX_SKILL_MD_SIZE` の行がなかった（→ Decision の論点 E）。

**この ADR は事後検証の記録である。** 3 つの上限値はいずれも、当初「導出なしの保険値」として置かれた。2026-07-30 に実測を採って初めて、値が妥当かを検証した。当初から検討していたかのようには書かない。「検討していなかった」という事実自体が記録に値するからである。

### 実測データ（2026-07-30 採取・n=134）

開発機にインストール済みの実 Skills パッケージ 134 件（`~/.claude/skills` と `~/.claude/plugins/cache` 配下で `SKILL.md` を持つディレクトリ）。

| 指標 | 最小 | 中央値 | p95 | 最大 | 現行上限 | 余裕 |
|---|---|---|---|---|---|---|
| `SKILL.md` 単体 | 140 B | 8.1 KB | 33 KB | **74 KB** | 1 MB | 14 倍 |
| ファイル数 | 1 | 4 | 66 | **320** | 500 | **1.6 倍** |
| 合計サイズ | 140 B | 28 KB | 1.1 MB | **5.6 MB** | 50 MB | 9 倍 |

エンコーディング: UTF-8 デコード失敗 0 件 / BOM 付き 0 件 / CRLF 0 件。

**標本の限界（この ADR を読むときの前提）**: この分布は「開発機にインストール済みの**公開** Skills」であり、社内で実際に登録される Skills の分布とは異なりうる。特に最大値 320 ファイル（Cloudflare 系スキル）は外部エコシステム由来で、社内製がこの規模に達するかは未知である。この限界を踏まえ、Decision に見直し基準を含める。

### 前提の再導出 — ADR-002 の「inode 枯渇」は採用案では成立しない

上限値の根拠を書こうとして、先に「**そもそも各上限は何を守っているのか**」を問い直す必要が生じた。ADR-002 Context の攻撃表には「ファイル数爆発 → inode 枯渇、ループ処理の停止」とある。実装（`services/zip_inspector.py` / `routes/skills.py`）を読み直した事実は次のとおり。

1. **サーバの inode は枯渇しない。** 案 B は `extract` / `extractall` を一切呼ばず、ファイルシステムに何も書かない。「inode 枯渇」は展開する世界（却下した案 A、またはダウンロードした人の手元）でのみ起きる
2. **ループ処理の停止・パース費用も `max_files` では守れていない。** `zipfile.ZipFile()` は生成時に central directory 全体を eager にパースし、全 `ZipInfo` を構築する。`max_files` のチェックはその**後**の `infolist()` ループで走る。パース費用を実際に抑えているのは `_read_upload` の生 50MB 上限（1 エントリ最低 46 バイト → 理論上限 ~110 万エントリ）であり、`max_files` が 500 でも 2000 でもこの露出は変わらない
3. **採用案で `max_files` が実際に守っているものは、次の 2 つだけである。**
   - **`file_tree` JSONB と詳細画面の肥大。** とくに**ゼロバイトファイルの洪水**は `file_size` の累積＝サイズ上限では検出できず、件数上限だけが止められる。**サイズと件数の上限は冗長ではなく直交している**
   - **中継点としての責任。** 保管した ZIP はいつか誰かがダウンロードして手元で展開する。数十万件の極小ファイルは、その人の環境で inode 枯渇・展開停止を起こす。これは `zip_inspector.py` が path traversal を弾く理由（「ダウンロードした人の手元で被害が出る」）と同一の論理であり、ADR-002 案 C の却下理由に既に書かれている思想である

これは ADR-002 の**内部矛盾というより根拠の置き忘れ**である。Context の攻撃表は ZIP 一般の攻撃カタログとしては正しい。しかし案 B を採用したあとに「では自分たちの実装で各上限は何に効くのか」へ翻訳されないまま、検証項目 4 の根拠のように読める位置に残った。ADR-002 の本文は**書き換えない**（ADR は記録である）。この再導出は本 ADR に記録し、ADR-002 のヘッダから参照できるようにする。

## Options Considered

### 論点 A: `MAX_FILES`（既定 500）をどうするか

#### 案 A-1: 2000 に引き上げる 〔採用〕

**Pros**

- **下限側の制約を満たす。** 実在する正当なパッケージ（320 件）を実余裕をもって受け入れられる。500 は余裕 1.6 倍で、パッケージ構成の自然な成長（ドキュメント追加等）で正当な入力が弾かれる位置にある
- **上限側の制約も満たす。** `file_tree` JSONB は 1 エントリ約 100 バイトと見積もって 2000 件で約 200KB（600 ファイルの実測は 27.6KB＝1 エントリ約 46 バイトで、見積もりは安全側に振れている）。DB 行・詳細画面の描画とも許容内。かつ誤混入の検出線として機能する（`node_modules` や `.venv` を誤同梱したパッケージは典型的に 5,000〜50,000 件で、2000 はその手前で止まる）
- 実測最大の 6.3 倍・p95 の 30 倍。サイズ側の余裕（9〜14 倍）と同水準を、**倍率の模倣ではなく機能要件から導いた値**として確保できる

**Cons**

- 受け入れる入力が広がる＝セキュリティ境界の変更であり、決裁が必要になる
- `file_tree` の想定サイズが 4 倍になる（約 50KB → 約 200KB）

**評価**: 複雑さ ◎（既定値 1 行） / コスト ◎ / **導出が機能要件に紐づく**

#### 案 A-2: 500 を維持し、根拠だけを書く

「320 は例外的、p95 66 の 7.6 倍で十分」という立論は可能。

**Pros**

- セキュリティ境界を動かさない。決裁が不要で、変更範囲がドキュメントだけに収まる
- 上限が薄いこと自体で不審な入力に早く気づける（と主張できる）

**Cons**

- その 320 が**実在の公開エコシステム由来**（Cloudflare 系）である以上、「例外」と呼ぶ根拠がない。むしろ本レジストリが受け入れるべき典型的な大型パッケージである
- 再導出（Context）のとおり、`max_files` が守っているもの（`file_tree` 肥大防止・中継点責任）はどちらも「500 でなければならない」を要求しない。**この薄さに protective な意味がない**
- 環境変数で運用回避はできるが、**既定値が実態と衝突していること自体**が「根拠を問われて答えられない」状態の再生産になる

**評価**: 却下。守っているものが 500 を要求しないのに、正当な入力を弾くリスクだけが残る

#### 案 A-3: 大きく引き上げる（10,000 以上）

**Pros**

- 正当な入力が弾かれる懸念がほぼ消える

**Cons**

- `file_tree` JSONB が 1MB 級になり、詳細画面が数万行を描画する
- 正当なパッケージがその領域に存在しない（実測最大 320）のに、表示・保存コストだけを受け入れることになる
- 誤混入（`node_modules` 同梱）の検出線として機能しなくなる
- 500 と同じ「導出のない数字」を、大きい側に置き直すだけである

**評価**: 却下

#### 案 A-4: 件数上限を撤廃し、サイズ上限だけで守る

**Pros**

- ノブが 1 つ減る。「冗長な上限を統合した」という見た目の単純さ

**Cons**

- **ゼロバイト洪水**（合計サイズ 0 のまま件数だけ爆発）がサイズ上限をすり抜ける。Context のとおり件数とサイズは直交する防御であり、片方に畳めない

**評価**: 却下

#### 案 A-5: 受入上限と表示上限を分離する（`file_tree` を切り詰めて表示）

**Pros**

- 「受け入れたいが表示しきれない」パッケージに理論上対応できる

**Cons**

- ノブが 2 つに増え、切り詰め UI という新部品が要る
- 分離が効くのはそういうパッケージが実在するときで、実測上そのケースがない（YAGNI）

**評価**: 却下

### 論点 B: `MAX_TOTAL_SIZE`（50MB）/ `MAX_SKILL_MD_SIZE`（1MB）をどうするか

#### 案 B-1: 値を維持し、事後検証であることを明示して根拠を記録する 〔採用〕

維持の立論（事後だが実質的な根拠）:

- **50MB**: 同期処理（[ADR-001](ADR-001-zip-parsing-sync-vs-async.md)）でメモリに全載せする設計のため、「同時アップロード数 × 50MB」が ECS メモリ見積もりの単位になっている（ADR-002 Consequences）。生アップロード上限（`_read_upload`）・展開後累積上限・ALB 経路設定の 3 か所が同じ値を共有しており、**変えるなら 3 点連動**。実測最大 5.6MB に対し 9 倍で、変える動機がない
- **1MB**: **唯一実際に解凍するファイル**（`SKILL.md`）の読み出し上限であり、ヘッダ偽装時の解凍露出の総量そのもの。かつ [ADR-007](ADR-007-store-skill-md-body.md) で DB の TEXT カラムに入る値の上限。実測最大 74KB に対し 14 倍

**Pros**

- 変更なしで済み、3 点連動のリスクを負わない
- 実測で余裕を確認できているので、「根拠はあるか」への答えが成立する

**Cons**

- 余裕（9〜14 倍）が過大に見える。当初から導出があったわけではないという弱さは残る（→ だからこそ時系列どおり書く）

**評価**: 採用

#### 案 B-2: 当初から検討していたように書く

**Cons**

- 読んだ人が「検討された値」だと誤解する。問いへの答えが「なかったので事後検証した」である以上、そのとおり書くのが唯一誠実な形である

**評価**: 却下（最優先の制約に反する）

#### 案 B-3: 値を実測に寄せて引き下げる（例: 10MB / 256KB）

**Pros**

- 余裕が実測に見合う

**Cons**

- 下げる実益（守れるものの増分）が具体化しない一方、境界を狭める変更は将来の正当な入力を弾くリスクだけを足す
- 標本の限界（社内分布は未知）がある今、**狭める判断こそ根拠不足**である

**評価**: 却下

#### 50MB の記述の在処について

ADR-001 Context の「実測で数十 KB〜数 MB。上限の 50MB は保険」という一行は**移動も削除もしない**（ADR は記録である）。本 ADR を値の根拠の正典とし、ADR-001 のその記述は「当時の見立て」として参照する。ADR-001 の Decision（同期処理）は本件の影響を受けないため、ADR-001 に `Amended by` は付けない。

### 論点 C: UTF-8 必須と BOM 除去をどうするか

#### 案 C-1: UTF-8 必須を維持し、BOM 除去も維持する 〔採用〕

**UTF-8 必須を維持する根拠**

1. frontmatter を YAML として解析し、`name` / `description` を PostgreSQL（UTF-8）・JSON レスポンス・`Content-Disposition` ヘッダへ流す**全経路が UTF-8 前提**である
2. `SKILL.md` を生成するエコシステム（Claude 系ツール）の出力は UTF-8 で、実測 134 件中デコード失敗 0 件＝**他エンコーディングの実需が観測されていない**
3. 拒否メッセージが明確（手動テスト No.14）で、利用者は保存し直すだけで回復できる

**BOM 除去（`split_frontmatter` の `lstrip`）を維持する根拠**

実測 0 件だが、Windows メモ帳等「UTF-8 with BOM で保存する既知の主要な生成源」が存在する。除去が無いと先頭の `---` 判定に落ちて「frontmatter がありません」という**原因の見えないエラー**になる。コストは 1 行＋既存テスト 1 件。**実測 0 件・防御的に維持**であることを隠さずここに記録する。

**Cons**

- 防御的措置が実測の裏付けなしに残る（＝この記録がないと、次の読み手が「なぜあるのか」を再度問うことになる）

**評価**: 採用

#### 案 C-2: `chardet` 等でエンコーディングを推測して受け入れる

**Cons**

- 推測の失敗は「**文字化けした `name` で登録される**」。`name` は同一性判定（`skills.name` UNIQUE）・検索・`Content-Disposition` に波及するため、明示的拒否より悪い**沈黙のデータ破損**になる
- 実需 0 件のために最悪の失敗モードを導入する取引は成立しない

**評価**: 却下

#### 案 C-3: Shift_JIS 等の限定的な追加受入

**Cons**

- 実需 0 件。受入を後から足すのは容易（デコード候補を増やすだけ）だが、**一度受け入れた形式を外すのは登録済みデータがある限り困難**。狭く始めるのが正しい側である

**評価**: 却下

#### 案 C-4: BOM 除去を外し、テストごと消す

**Cons**

- 動作中・無害・テスト済みのコードを純粋性のために消すのは、変更リスクだけを足す
- 除去した場合の失敗モード（原因の見えないエラー）が悪質である

**評価**: 却下

### 論点 D: `docs/design.md` §7 の記載漏れをどう防ぐか

#### 案 D-1: `Settings` 全フィールドとの 1:1 対応を規則化し、テストで機械的に強制する 〔採用〕

`Settings.model_fields` の各フィールド名（大文字化した環境変数名）が `docs/design.md` に出現することを assert する（`backend/tests/test_docs_consistency.py`）。

**Pros**

- 判断が発生しない機械的規則なので、次のフィールド追加でも漏れない
- learnings #9 の教訓「メモではなく仕組みで防ぐ」をテストで満たす

**Cons**

- テストがリポジトリのディレクトリ構造（`backend/../docs/`）に依存する

**評価**: 採用

#### 案 D-2: 漏れた 1 行だけ足す

**Cons**

- 今回の漏れ自体が「§7 に何を載せるかの基準が無い」ことの帰結である。基準なしで行だけ足せば、次のフィールド追加でまた漏れる

**評価**: 却下

#### 案 D-3: 「重要な変数を載せる」等、判断を要する基準を文章で定義する

**Cons**

- 「重要」の判定が人によって揺れ、漏れの温床が残る

**評価**: 却下

#### 案 D-4: §7 の表を `config.py` から自動生成する

**Cons**

- 生成スクリプト・ビルド手順という新部品が増える。パリティの検証（テスト）だけで漏れは防げるので、道具立てが過大

**評価**: 却下

## Decision

**この節の内容は、実装当初からの導出ではなく、2026-07-30 の実測（n=134）による事後検証の結果である。**

1. **`MAX_FILES` の既定を 500 → 2000 に引き上げる。** 導出は Context の再導出（`file_tree` 肥大防止・中継点責任）と、下限側（実在パッケージ 320 件の受入）・上限側（`file_tree` 約 200KB・誤混入の検出線）の機能要件から。倍率の模倣ではない
2. **`MAX_TOTAL_SIZE` は 50MB を維持する。** 実測最大 5.6MB に対し 9 倍。生アップロード上限・展開後累積上限・ALB 経路設定の 3 か所が同じ値を共有しており、変えるなら 3 点連動
3. **`MAX_SKILL_MD_SIZE` は 1MB を維持する。** 唯一実際に解凍するファイルの読み出し上限＝ヘッダ偽装時の解凍露出の総量。実測最大 74KB に対し 14 倍
4. **UTF-8 必須を維持する。** 全経路が UTF-8 前提で、他エンコーディングの実需が観測されていない。推測受入は「沈黙のデータ破損」を招くため採らない
5. **BOM 除去は維持する。これは実測 0 件の防御的措置である。** 既知の生成源（Windows メモ帳等）があり、無いと原因の見えないエラーになる
6. **`docs/design.md` §7 は `Settings` 全フィールドと 1:1 対応させる。** 規則を §7 冒頭に明記し、`backend/tests/test_docs_consistency.py` で機械的に強制する

### 見直し基準（[ADR-001](ADR-001-zip-parsing-sync-vs-async.md) の「移行基準」と同じ流儀）

`MAX_FILES = 2000` は次のいずれかが起きた時点で見直す。

1. **正当なパッケージが 413 で弾かれる事例が 1 件でも出たとき**
2. **登録された正当なパッケージの最大ファイル数が上限の 50%（1000 件）を超えたとき**
3. **社内の実登録分布が採れた時点**（標本の限界の解消）で再計測したとき

## Consequences

- `backend/app/core/config.py` の `max_files` 既定が `2000` になる。コメントは「走査コストの爆発を防ぐ」ではなく、再導出後の根拠（`file_tree` 肥大防止・中継点責任）を指す
- 手動テスト No.09 の期待メッセージが「上限（2000 件）」に変わる。`backend/scripts/make_test_zips.py` の 09 は 2001 ファイルの ZIP を生成する
- `docs/design.md` §4 の 413 の説明・§7 の `MAX_FILES` が 2000 に揃う。§7 に `MAX_SKILL_MD_SIZE` の行と 1:1 規則の 1 文が入る
- **`MAX_TOTAL_SIZE`（50MB）を変えるときは 3 か所連動**（`_read_upload` の生上限・展開後累積上限・ALB 経路設定）。1 か所だけ変えると、遮断される層がずれる
- `Settings` にフィールドを足すと `test_docs_consistency.py` が落ちる。これは仕様である（`docs/design.md` §7 に行を足せば通る）
- ADR-002 は `Accepted` のまま `Amended by ADR-008` を付す。**Decision（案 B = in-memory 検査）は覆っていない**ため Superseded ではない。本文の「既定 500 件」の記述は 2026-07-29 時点の決定の記録としてそのまま残す
- 引き上げ後に問題（不審な大量ファイル ZIP の受入等）が観測された場合は、コード変更なしで環境変数 `MAX_FILES=500` を設定して再起動すれば旧値へ戻せる。恒久対応はその観測を Context に足して本 ADR を見直す
- `docs/learnings.md` #5（zip bomb はヘッダで安価に弾き、実読み出しは別途上限で守る）/ #6（表示からは除くが集計には含める）は、本 ADR の上限値がどの層で効くかの実地の記録である。ADR へ昇格させず、ここから参照する
