# ADR-004: 検索は PostgreSQL の `ILIKE` で実装する

- **Status**: Accepted
- **Date**: 2026-07-29

## Context

一覧画面に検索ボックスとタグ絞り込みを置く。検索対象は Skills の `name` と `description`（`SKILL.md` の frontmatter 由来）で、どちらも短い文字列である。

想定データ量:

- 社内の Skills パッケージ。**当面は数十〜数百件**、多く見積もっても数千件
- 1 レコードあたりのテキストは合わせて数百文字

検索の性質:

- 「あの Slack 通知のやつ」を探す **既知アイテムの再発見** が主用途。未知の文書を掘り出す全文検索ではない
- 日本語と英語が混ざる

この規模では、どの方式を選んでも体感の応答速度は変わらない。したがって判断基準は速度ではなく「**運用コストと、必要になったときの移行しやすさ**」になる。

## Options Considered

### 案 A: `ILIKE '%q%'`（PostgreSQL 標準）

```sql
WHERE name ILIKE '%' || :q || '%' OR description ILIKE '%' || :q || '%'
```

**Pros**

- 追加の拡張機能もインフラも不要。素の PostgreSQL 16 でそのまま動く
- **部分一致が直感どおりに効く**。日本語のように単語境界が空白で示されない言語でも、「通知」で「Slack通知」がヒットする
- SQLAlchemy の `.ilike()` で数行。理解・レビューのコストがほぼゼロ
- 大文字小文字を区別しない（`ILIKE` の I）ので、英語の Skills 名でも取りこぼさない

**Cons**

- 前方一致でない `%q%` は **B-tree インデックスが効かず、常にシーケンシャルスキャン**になる。件数が増えれば線形に遅くなる
- 関連度スコアがない。並び順は自分で決めるしかない（今回は更新日時降順）
- `%` `_` がユーザー入力に含まれるとワイルドカードとして解釈される（→ エスケープが必要）

**評価**: 複雑さ ◎ / コスト ◎ / 習熟度 ◎

### 案 B: `tsvector` による全文検索（PostgreSQL 標準）

`to_tsvector` / `to_tsquery` と GIN インデックス。

**Pros**

- インデックスが効き、件数が増えても速い
- `ts_rank` で関連度順に並べられる
- ステミング（`running` → `run`）など言語処理が入る

**Cons**

- **日本語が実質的に機能しない**。PostgreSQL 標準の parser は空白で区切る前提のため、「Slack通知を送る」が 1 トークンになってしまう。日本語を扱うには pgroonga や textsearch_ja といった **追加拡張が必要**で、それは Docker イメージのビルドから見直す話になる
- 部分一致の直感と合わない。「通知」で検索して「Slack通知」が出ないのは、利用者にはバグに見える
- クエリのエスケープ（`to_tsquery` の構文）を自前で処理する必要がある

**評価**: 複雑さ △ / コスト ○ / 習熟度 △。そして **日本語という要件で正面から詰まる**

### 案 C: `pg_trgm` + GIN インデックス

3-gram でトークン化し、`%q%` の LIKE 検索にインデックスを効かせる拡張。

**Pros**

- **`ILIKE` の使い勝手をそのままに、インデックスが効く**。案 A の唯一の弱点（線形スキャン）だけを解消する
- 日本語でも 3-gram なので部分一致が機能する
- `similarity()` であいまい検索（タイポ許容）もできる
- `CREATE EXTENSION pg_trgm;` の 1 行で有効化でき、PostgreSQL の contrib に同梱されている

**Cons**

- 拡張の有効化が必要（マイグレーション or 初期化 SQL に 1 行）
- GIN インデックスの構築・更新コストがかかる。数十件の規模では **インデックスを引くより全件走査のほうが速い**（プランナも seq scan を選ぶ）ので、現時点では純粋にオーバーヘッド

**評価**: 複雑さ ○ / コスト ○ / 習熟度 ○。**案 A の自然な次の一手**

### 案 D: OpenSearch / Elasticsearch

**Pros**

- 検索機能としては最上位。日本語形態素解析（kuromoji）、ファセット、ハイライト、関連度チューニング

**Cons**

- **クラスタの運用コストが、レジストリ本体より重くなる**。数百件のために立てるものではない
- DB とインデックスの同期（インデクシングパイプライン、再構築、整合性）という新しい問題領域が丸ごと増える
- マネージド（OpenSearch Service）でも月額の固定費が発生する

**評価**: 却下（規模に対して過剰。運用コストが機能価値を上回る）

### 案 E: pgvector による意味検索

埋め込みベクトルで「意味が近い Skills」を返す。

**Pros**

- 「Slack に通知したい」で `notify-chat` がヒットするような、語彙が一致しない検索に強い

**Cons**

- 埋め込み生成に外部 API 呼び出し（＝コストとレイテンシと障害点）が要る
- アップロード時に埋め込みを作り、モデル更新時には全件再生成する運用が必要
- **主用途は既知アイテムの再発見**であり、語彙は利用者の頭に入っている。意味検索が解決する問題を今は抱えていない

**評価**: 却下（今回は要件がない）。ただし将来の拡張先としては筋が良い

## Decision

**案 A（`ILIKE` による部分一致）を採用する。**

理由は「数百件の規模では方式間の体感差がゼロだから、最も理解しやすく依存の少ないものを選ぶ」に尽きる。案 C（pg_trgm）は明確に上位互換だが、**その利点（インデックス）が効き始めるのは数千件からで、今それを入れても得るものがない**。ここで案 C を選ばないのは性能の判断ではなく、「効果が出ない最適化を先に入れない」という判断である。

実装上の注意:

- `%` と `_` を **エスケープしてから** `ILIKE` に渡す。ユーザーが `_` を含む Skills 名を検索したときに意図せず 1 文字ワイルドカードになるのを防ぐ（SQL インジェクションはバインドパラメータで防げるが、ワイルドカード解釈はそれとは別の問題）
- タグ絞り込みは `skill_tags` の JOIN による完全一致。こちらは正規化済みなのでインデックスが効く
- 並び順は「最新版の作成日時の降順」で固定する。関連度スコアがない以上、順序は説明可能な単純な規則にしておく

## 拡張パス（この判断を見直す順序）

段階を明示しておくことで、「いきなり OpenSearch」という飛躍を避ける。

1. **件数が数千件を超え、一覧の応答が体感で遅くなる** → `CREATE EXTENSION pg_trgm` + GIN インデックス（案 C）。**アプリのクエリは `ILIKE` のまま変更不要**。これが案 A を選ぶもう一つの理由で、次の一手がアプリ変更なしで打てる
2. **日本語の検索品質そのものが問題になる**（部分一致では拾えない表記ゆれ・活用形） → pgroonga、または外部の検索エンジン
3. **語彙が一致しない検索が必要になる**（自然文で探したい） → pgvector による意味検索を `ILIKE` と併用（ハイブリッド検索）

## Consequences

- 検索の実装は `skill_service.py` の 1 クエリに収まる。専用のインフラも同期処理も持たない
- 一覧 API は `GET /skills?q=&tag=` の 2 パラメータ。フロントは Server Component で `searchParams` を読んでサーバ側で再取得する（ADR-005）
- 性能特性は「件数に線形」であることを README / design.md に明記する。**性能の前提を書き残しておかないと、後任者が原因を探すところから始めることになる**
- インデックスを張らないという判断も明示的な選択なので、`skills.name` の UNIQUE 制約（同名判定に使う）以外に検索用インデックスは作らない
