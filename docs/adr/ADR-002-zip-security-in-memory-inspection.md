# ADR-002: ZIP をディスクに展開せず in-memory で検証する

- **Status**: Accepted
- **Date**: 2026-07-29
- **Amended by**: [ADR-008](ADR-008-validation-limits-and-utf8.md)（上限値の根拠を再導出し `MAX_FILES` の既定を変更。in-memory 検査という Decision は不変）

## Context

このレジストリは **外部から与えられたアーカイブを受け取る** システムである。ZIP は攻撃者にとって扱いやすい入力形式で、古典的な攻撃手法が揃っている。

| 攻撃 | 内容 | 起きること |
|---|---|---|
| Path traversal（Zip Slip） | エントリ名が `../../etc/cron.d/x` や `/etc/passwd` | 展開時に **アーカイブ外へファイルを書き込む**。任意ファイル上書き → RCE に繋がる |
| Symlink 攻撃 | ZIP 内に `/etc/shadow` を指す symlink を含める | 展開後にその symlink を辿って読み書きし、ホストのファイルを窃取・改竄 |
| Zip bomb | 高圧縮率のデータ（42.zip 等） | 展開でディスク / メモリを食い潰し DoS |
| ファイル数爆発 | 極小ファイルを数十万件 | inode 枯渇、ループ処理の停止 |
| ドライブレター / バックスラッシュ | `C:\Windows\...`、`..\..\x` | 一部の展開実装で traversal になる |

さらに重要な前提として、**このレジストリは Skills を実行しない**。保管と配布のみを行う。これはセキュリティ境界であり、恒久的な非機能要件として扱う（ADR で明示しておく価値がある。「将来 Skills をサーバ側で試せるようにしたい」という要望が来たときに、ここへ立ち返るため）。

したがって守るべきは「**受け取った ZIP の中身を、こちらのファイルシステムに一切具現化しない**」という一点になる。

## Options Considered

### 案 A: 一時ディレクトリに展開してから検証する

`tempfile.TemporaryDirectory()` を作り `zf.extractall()`、その後に中身を検査する。

**Pros**

- 実装が直感的。展開後は普通のファイル操作で `SKILL.md` を探せる
- 既存のファイル走査ライブラリ（`pathlib.rglob` 等）がそのまま使える

**Cons**

- **検証より先に展開が起きる**という順序が致命的。`extractall()` 自体が攻撃対象になる（Python の `extractall` は traversal をある程度は無害化するが、symlink の扱いは版とプラットフォームに依存し、依存先の挙動に安全性を委ねる形になる）
- zip bomb はディスクを実際に食ってから気づくことになる。ECS の ephemeral storage を埋めるとタスク全体が死ぬ
- 一時ファイルの後始末が例外経路も含めて必要。消し漏れが積み上がる
- 「安全かどうか」がアプリのコードではなく **標準ライブラリと OS の組み合わせ** で決まるため、レビューで安全性を論証しにくい

**評価**: 複雑さ △（後始末が要る） / コスト ○ / 習熟度 ◎ だが **安全性が構造的でない**

### 案 B: 展開せず、`zipfile` のメタデータとストリーム読み出しだけで検証する

`zipfile.ZipFile(io.BytesIO(data))` を開き、`infolist()` の各 `ZipInfo` を検査する。中身が必要なファイル（`SKILL.md`）だけを `zf.read(info)` でメモリに読む。**`extract` / `extractall` は一切呼ばない。**

**Pros**

- **ファイルシステムに何も書かないので、展開起因の攻撃がそもそも成立しない**。path traversal も symlink も「書き込む先」がない以上、無害な文字列・属性値に過ぎなくなる
- zip bomb は `ZipInfo.file_size`（展開後サイズ）の **累積をヘッダから読むだけ** で、1 バイトも解凍せずに判定できる
- 一時ファイルが無いので後始末が不要。例外経路での消し漏れが原理的に起きない
- 検査ロジックが `bytes` → 検査結果の純粋関数になり、テストが容易（ADR-001 の「後からワーカーへ移せる」という前提とも噛み合う）

**Cons**

- 50MB の ZIP をメモリに載せる。同時アップロード数 × 50MB のメモリ見積もりが必要
- `zipfile` の低レベル API（`external_attr` のビット演算など）を自分で扱う必要があり、実装者が仕様を理解していないと穴が空く
- ZIP のヘッダ（`file_size`）は自己申告値であり、それ自体は偽装できる（→ 後述の二重チェックで補う）

**評価**: 複雑さ ○（低レベル API の理解が要る） / コスト ◎ / 習熟度 ○ で、**安全性が構造的**

### 案 C: 検証しない / サイズ上限だけ設けて丸ごと保管する

「実行しないのだから中身は何でもよい」と割り切り、ZIP をそのまま保存する。

**Pros**

- 実装が最小

**Cons**

- レジストリとしての価値がない。`SKILL.md` を読めないので名前・説明・タグが取れず、一覧も検索も成立しない
- 保管したものは **いつか誰かがダウンロードして展開する**。危険なアーカイブを社内へ配る中継点になる。「実行しないから安全」は自分のサーバの話でしかなく、利用者への責任を果たしていない

**評価**: 却下（機能要件を満たさない上に、リスクを利用者へ転嫁する）

### 案 D: 外部のサンドボックス / ウイルススキャナに委ねる

ClamAV コンテナや外部 API に ZIP を渡して判定する。

**Pros**

- 既知マルウェアの検出という、自前実装では到底届かない層を担える

**Cons**

- **構造的な検証（traversal / bomb）の代替にはならない**。守る対象が違い、案 B と排他ではなく直交する
- 常時稼働のスキャナコンテナ or 外部依存が増え、処理時間も秒オーダーになる（ADR-001 の同期処理という判断に抵触する）

**評価**: 今回は対象外。将来 ClamAV を足すなら ADR-001 の移行基準 3 に該当し、非同期化とセットで検討する

## Decision

**案 B（ディスク非展開・in-memory 検査）を採用する。**

決め手は「安全性をコードの構造で担保できる」こと。案 A は正しく書けば安全にできるが、その正しさは `extractall` の実装詳細と OS の挙動に依存し、レビューで論証しづらい。案 B は **書き込み処理が存在しない** ので、「traversal で何が起きるか」を議論する必要すらない。攻撃面をゼロにするほうが、攻撃を検知するより強い。

### 検証項目（`services/zip_inspector.py` の責務）

すべてのエントリについて、以下を **read の前に** 検査する。

1. **ZIP として開けること** — 開けなければ 400
2. **エントリ名の健全性** — 絶対パス（`/` 始まり）、`..` を含むパス、バックスラッシュ、ドライブレター（`C:`）を拒否
3. **symlink の拒否** — `(info.external_attr >> 16) & 0o170000 == 0o120000`（`stat.S_IFLNK`）で判定。UNIX 由来の ZIP は上位 16bit にモードが入る
4. **ファイル数上限** — 既定 500 件。超過は 413
5. **展開後合計サイズ上限** — 既定 50MB。`info.file_size` を累積し、上限超過時点で **即座に打ち切る**（全件走査を待たない）
6. **`SKILL.md` の特定** — ルート直下、または 1 階層下のディレクトリ直下のみを対象。0 件なら 422、複数該当なら「どれが正か決められない」ため 422
7. **frontmatter の検証** — `SKILL.md` のみ `zf.read()` し、`---` で挟まれた YAML ブロックを取り出して `name` / `description` の存在を確認。不正なら 422

### `file_size` 自己申告問題への対応

ZIP ヘッダの `file_size` は攻撃者が偽装できる。そこで **ヘッダ値による事前遮断** と **実読み出し時の実測** を二重に行う:

- ヘッダの累積 `file_size` が上限を超えたら、解凍せずその場で拒否（安価な第一関門）
- 実際に読むのは `SKILL.md` ただ 1 ファイルであり、その読み出しにも上限を課す（`zf.open()` からの `read(limit + 1)` で、上限を 1 バイトでも超えたら中断）

「全ファイルを読まない」ので、ヘッダ偽装で実サイズが膨らんでいても、こちらが解凍する量は `SKILL.md` の上限までに抑えられる。

## Consequences

- ZIP は **原本のみ** をストレージへ保存する。展開後のファイルは保存しない（配布はアーカイブ単位でよい、というプロダクト判断とも一致）
- ファイルツリー表示は `infolist()` から組み立てた JSON（`file_tree`）を DB に持つ。詳細画面のためだけに ZIP を再度開かなくて済む
- メモリ使用量は「同時アップロード数 × ZIP サイズ」で見積もる。ECS タスクのメモリ設定時にこの前提を思い出せるよう、`MAX_TOTAL_SIZE` は環境変数で外出しする
- **Skills をサーバ側で実行する機能は恒久的に対象外**とする。実行が必要になった場合、それはこのレジストリの責務ではなく、隔離された別システムの設計課題として起票する
- 検査の各項目には 1 対 1 でテストを書く。特に path traversal のテストは、通常の `zipfile.write()` では危険なエントリ名を作れないため、**`ZipInfo` を直接組み立てて `writestr()` する**（テストヘルパー `make_skill_zip()` に集約）
