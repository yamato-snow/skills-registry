# ADR-006: 検索の複数語 AND・関連度・スニペット — `ILIKE` を維持したまま当たり方の質を上げる

- **Status**: Accepted
- **Date**: 2026-07-29
- **Amends**: [ADR-004](ADR-004-search-postgres-ilike.md)（`ILIKE` 採用と拡張パスは維持したまま、決定の範囲を広げる）

## Context

[ADR-004](ADR-004-search-postgres-ilike.md) で `ILIKE` による部分一致を採用し、フェーズ 1 ではそのまま「`q` を 1 つの文字列として `name` / `description` に当てる」実装になっている。動くものを触って分かったのは、**遅いのではなく当たり方が雑**だということだった。

現状で起きること:

- `slack 通知` と 2 語で打つと、その 8 文字がそのまま連続して現れる Skill しか出ない。**語を足すほど絞れる**という検索の基本的な期待が裏切られる
- 全件が同じ「更新日時降順」で並ぶ。`slack-notifier` という名前ずばりの Skill が、説明文にたまたま `slack` と書いてある別の Skill より下に来る
- `SKILL.md` の本文は検索対象になっていない。「description には書いていないが本文には書いてある」は、既知アイテムの再発見（ADR-004 が主用途と定義したもの）でまさに起きる
- タグは 1 つしか指定できない

登録件数は現在 3 件。**この規模で速度の問題は存在しない**。したがって今回の設計原理は「速度ではなく当たり方の質」であり、性能施策は一切入れない。

## Options Considered

### 案 A: `ILIKE` のまま、複数語 AND・関連度順・スニペットの 3 点を実装する

`q` を空白で分割し、トークンごとに `(name ILIKE ? OR description ILIKE ? OR body ILIKE ?)` を作って AND で重ねる。並び順とヒット箇所の判定は Python の純粋関数で行う。

**Pros**

- **問題として観測されているものだけを直す**。速度は問題になっていないので触らない
- SQL は絞り込みだけを担当し、順位の規則は 1 つの Python 関数に収まる。**DB を立てずに順位のテストが書ける**
- ADR-004 の拡張パス（pg_trgm → 全文 → ベクトル）をそのまま温存できる。クエリの形は `ILIKE` のままなので、いつ pg_trgm を入れても効く

**Cons**

- 絞り込み済みの行を Python 側で並べ替えるので、件数がスコア計算に線形で効く。ただし絞り込み自体が既に seq scan（ADR-004 で受け入れ済み）なので、**計算量クラスは変わらない**

**評価**: 複雑さ ◎ / コスト ◎ / 習熟度 ◎

### 案 B: `pg_trgm` を入れる（インデックス＋ `similarity()` によるタイポ許容）

**Pros**

- ADR-004 が「自然な次の一手」と書いた案そのもの。インデックスが効き、`similarity()` で表記ゆれも拾える

**Cons**

- ADR-004 の第一拡張トリガーは「**数千件超＋体感遅延**」。3 件の現在にその根拠はない
- タイポ許容という別の根拠も検討したが、**利用者が実質 1 人・登録名も自分で付けた名前**という現状では「表記ゆれで見つからない」実害が観測されていない
- 観測されていない問題への先行投資は、ADR-004 の決め手だった「**効果が出ない最適化を先に入れない**」という判断そのものに反する

**評価**: 却下（今回は）。実害が出た時点で ADR-004 拡張パス 1〜2 の中で再検討する

### 案 C: SQL 側でスコアリングする（`CASE` 式の重み付け）

```sql
ORDER BY (CASE WHEN name ILIKE ? THEN 3 WHEN description ILIKE ? THEN 2 ... END) + ... DESC
```

**Pros**

- 並べ替えまで DB に任せられる。将来ページネーションを入れるなら、順位が SQL 側にあるほうが素直

**Cons**

- トークン数 × フィールド数だけ枝が増える**巨大な CASE 式**になり、テストするには毎回 DB が要る
- 結果は案 A と同一。件数線形を受け入れている現状では、絞り込み済みの行を Python で並べ替えても計算量クラスは変わらない

**評価**: 却下。ただし **移行先としては正しい**（下記「移行の条件」）

### 案 D: `tsvector` / pgroonga / OpenSearch / pgvector

ADR-004 で却下済み。日本語の部分一致・運用コスト・要件の不在という理由はいずれも変わっておらず、覆す新事実がない。

**評価**: 却下（判断を覆す材料なし）

## Decision

**案 A を採用する。** `ILIKE` を検索プリミティブとして維持したまま、次の 3 つを実装する。

### 1. 複数語 AND 検索

`q` を空白で分割し、**全トークンが `name` / `description` / 本文のいずれかに当たる** Skill だけを返す。

- 分割は Python の引数なし `str.split()`。これは Unicode の空白全般で分割するので、**全角空白（U+3000）も追加の処理なしに扱える**。日本語入力では半角と全角が混ざるので、ここを取りこぼすと「打ったのに出ない」になる
- 各トークンは既存の `escape_like()` でエスケープする（ADR-004 の実装上の注意をそのまま適用）
- **OR 検索・AND/OR 切り替えは入れない**。3 件の規模で「広げる」操作に実需がなく、トグルの選択状態という途中状態を持つ Client Component が増えるだけになる（ADR-005 の基準）

### 2. 関連度順

順位の規則は一行で説明できる範囲に留める。**説明できない順位は苦情の元になる**。

> トークンごとに `name` ヒット = 3 点 / `description` = 2 点 / 本文 = 1 点の **最高点だけ**を数え、それを全トークン分足す。同点は最新版の `created_at` 降順。

- 最高点だけを取るのは、同じ語が `name` と本文の両方に出ているだけで順位が跳ね上がるのを防ぐため
- SQL が既に「更新日時降順」で返しているので、Python の**安定ソート**でスコア降順に並べ替えれば、同点時の順序は自動的に日時降順になる。同点の規則を別途書く必要がない
- **`q` が無いときは従来どおり更新日時降順**。挙動が変わらないので、フェーズ 1 の一覧テストは 1 行も直さずに緑のまま

### 3. ヒット箇所の可視化

一覧 API が `q` 指定時に `matched_fields`（`name` / `description` / `body` の配列）と `snippet`（本文ヒット時、最初のヒット位置の周辺 ±40 文字）を返す。

本文にしか当たっていないヒットは、**一覧だけ見ても「なぜこれが出たのか」が分からない**。その理由をその場で示すのがこの 2 つの役目で、本文に当たっていなければ `snippet` は `null` を返す（説明することがない）。

ハイライトの描画はフロント側の純粋関数で行い、テキストを分割して React 要素として組み立てる。`dangerouslySetInnerHTML` は使わない（[ADR-007](ADR-007-store-skill-md-body.md) と同じ理由）。

### 実装上の位置

スコアリング・ヒット箇所判定・スニペット抽出は `app/services/search.py` に置き、**FastAPI にも SQLAlchemy にも依存させない**。`zip_inspector.py` と同じ扱いにする理由も同じで、DB を立てずに単体で検証しきれることに価値があるため。

**Python 側の部分一致判定は SQL の `ILIKE` と同じ結果でなければならない**（どちらも大文字小文字を区別しない）。ずれると「一覧には出るのにハイライトされない」という説明のつかない状態になる。フロントの `tokenizeQuery()` がバックエンドの `tokenize()` と同じ分割をする必要があるのも同じ理由で、JavaScript の `\s` は U+3000 を含むので分割位置が一致する。

## タグの複数指定

`tag` を**繰り返しパラメータ**（`/?tag=slack&tag=notification`）で複数受け取り、**意味は AND**（絞り込みを重ねる操作として自然なほう）にする。タグごとに `EXISTS` を重ねることが、そのまま AND の意味になる。

UI は Server Component の `<Link>` チップで実装する。「このタグを足した URL / 外した URL」はサーバ側で計算できる純粋な導出値であり、クリック＝遷移＝サーバ再取得で完結する。**途中状態が存在しないので Client 化する理由がない**（ADR-005 の基準を機械的に適用した帰結）。結果として、**今回の機能追加で Client Component は 1 つも増えていない**。

## 移行の条件（この判断を見直す順序）

ADR-004 の拡張パスはそのまま生きている。それに加えて、スコアリングの置き場所についての移行先を書いておく。

1. **件数が数千件を超え、一覧の応答が体感で遅くなる** → ADR-004 拡張パス 1（`pg_trgm` + GIN）。`ILIKE` のままインデックスが効く
2. **1 を入れてもなお遅い、またはページネーションが必要になる** → スコアリングを SQL 側へ移す（案 C）。全件を Python に載せてから並べ替える構造は、ページ単位で取り出す要件と相性が悪いため
3. **表記ゆれ・タイポで見つからない実害が観測される** → `pg_trgm` の `similarity()` を併用

## Consequences

- ADR-004 の Decision（`ILIKE` 採用）は**覆っていない**ので、ADR-004 の Status は `Accepted` のまま維持し、ヘッダに `Amended by ADR-006` を追記する
- 検索の実装は `skill_service.list_skills()`（絞り込み）と `services/search.py`（順位・説明）の 2 箇所に分かれる。**どちらが何を決めているかを一行で言えること**が、この分け方を維持する条件
- 一覧 API のレスポンスに `matched_fields` / `snippet` が増える。`q` 無しのときは空配列 / `null` になるので、既存の呼び出し側は無視できる
- 本文を検索対象にできるのは [ADR-007](ADR-007-store-skill-md-body.md) で本文を DB に保存したため。この 2 本は同時に決めないと成立しない
