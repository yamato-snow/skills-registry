# 実装メモ（ハマった点・迷った判断）

実装しながら書き足したもの。結論だけ整理して書き直すと「なぜ最初にそう書かなかったのか」が消えてしまうので、詰まった順に率直に残す。

---

## 1. SQLAlchemy async の `MissingGreenlet` — flush 直後のインスタンスは触ってはいけない

**症状**: API テストの登録系だけが `sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here` で落ちた。単体テストは全部緑。

**原因**: 新規 `Skill` を `db.add()` → `await db.flush()` した直後に `skill.versions` を読んでいた。flush でインスタンスは persistent になるが、リレーションは **未ロード**のまま。そこへ属性アクセスすると SQLAlchemy は暗黙の遅延ロード（＝ SQL 発行）を試みる。同期 ORM ならこれは普通に動くが、async ではその I/O を `await` できないので例外になる。

**対処**: flush の後に `selectinload` 付きで取り直す。同一トランザクション内なので直前の INSERT は見える。

```python
db.add(Skill(name=package.name))
await db.flush()
skill = await _get_skill_by_name(db, package.name)  # 関連をロード済みにして取り直す
```

**学び**: async ORM では「属性を読む」が I/O になりうる。関連を触る予定があるなら、**どの時点でロード済みなのか**を意識しておく必要がある。同じ理由で `expire_on_commit=False` も必須で、これを外すと commit 後にレスポンスを組み立てる箇所が全部同じ例外で落ちる。

## 2. カバレッジが嘘をつく — greenlet を宣言しないと `await` の次の行が「未実行」になる

**症状**: テストは通っているのに、`register_skill` の中身がカバレッジ 0 行として報告された。しかも `await db.execute(...)` の**行だけ**は実行済みで、その**次の行から**未実行になっている。

**原因**: SQLAlchemy の async は内部で greenlet を使って同期 ORM を駆動する。coverage.py はグリーンレット間の切り替えを既定では追跡しないので、await から戻ってきた後のトレースが落ちる。

**対処**: `pyproject.toml` に 1 行。

```toml
[tool.coverage.run]
concurrency = ["thread", "greenlet"]
```

これで全体 65% → 99% になった。**コードもテストも 1 行も変えていない。**

**学び**: カバレッジの数字が直感と食い違ったとき、まず疑うべきは「テストが足りない」ではなく「計測できていない」かもしれない、ということ。この設定を知らないままカバレッジ閾値を CI に入れていたら、通すために意味のないテストを足していたかもしれない。

## 3. `.gitignore` の `storage/` が `app/storage/`（実装コード）まで飲み込んだ

アップロード先を無視するつもりで書いた `storage/` が、末尾スラッシュのみ・先頭スラッシュなしのパターンだったため、**リポジトリ内のあらゆる階層の `storage/`** にマッチした。`git add backend/app/storage` が拒否されて気づいた。

`/storage/` と書けばリポジトリ直下だけになる。`git add` が「ignore されています」と言ってくれたので早く気づけたが、これが `git add -A` だけの運用だったら、実装ファイルが 1 ディレクトリ丸ごとコミットされないまま進んでいた可能性がある。

## 4. ZIP の危険なエントリは、普通の書き方では作れない

path traversal のテストを書こうとして最初に詰まった。`zf.writestr("../../evil", ...)` は動くが、環境によっては正規化されうるし、symlink に至っては通常 API で作る方法がない。

`ZipInfo` を直接組み立てるのが答えだった。symlink は「`external_attr` の上位 16bit に `S_IFLNK` を立て、中身にリンク先の文字列を入れる」という表現になっている。この構造を理解して初めて、検出側のコード（`stat.S_ISLNK(info.external_attr >> 16)`）が何を見ているか腑に落ちた。

```python
info = zipfile.ZipInfo("secret")
info.external_attr = (stat.S_IFLNK | 0o777) << 16
zf.writestr(info, "/etc/shadow")
```

**攻撃の作り方を知らないと、防御が正しいか確かめられない。** テストヘルパーを書く作業がそのまま ZIP 仕様の理解になった。

## 5. zip bomb は「解凍しない」ことでしか防げない

展開後 60MB の ZIP を作っても、ゼロ埋めなら実ファイルは数十 KB にしかならない。もし「展開してからサイズを測る」実装にしていたら、この 60MB を実際にディスクへ書いてから気づくことになる。

`ZipInfo.file_size`（展開後サイズ）は**ヘッダに書かれた値**なので、1 バイトも解凍せずに合計を出せる。この事実が ADR-002 の「展開しない」判断を支えている。

ただしヘッダ値は攻撃者が偽装できるので、実際に読む `SKILL.md` には独立した上限を課している（`read(limit + 1)` で超過検出）。**ヘッダを信じて安価に弾き、実読み出しは別途上限で守る**、という二段構えになった。

---

## 6. macOS の `__MACOSX/` を「除外」すると穴になる

Finder で作った ZIP には `__MACOSX/._SKILL.md` が入る。ファイルツリーの表示に出すと利用者が混乱するので除外したが、**サイズと件数の集計からも外そうとして手が止まった**。

集計から外すと、そこに zip bomb を仕込めば上限チェックをすり抜けられる。結論は「**表示からは除く、集計には含める**」。UX のための除外が、そのままセキュリティの穴になりうる例だった。

---

## 7. `%` のエスケープは SQL インジェクション対策とは別の話

`ILIKE '%' || :q || '%'` はバインドパラメータを使っているので SQL インジェクションは起きない。しかし `q` に `%` が入ると、それはワイルドカードとして解釈されて全件マッチになる。

利用者が `my_skill` を検索したとき、`_` を「任意の 1 文字」のつもりで打っている人はいない。**「安全である」と「意図どおり動く」は別の要件**で、前者を満たしても後者は自動的にはついてこない。

---

## 8. compose のポートは固定しないほうがいい

`8000:8000` と書いていたら、同じマシンで動いている別プロジェクトのコンテナと衝突して起動できなかった。エラーメッセージ（`Bind for :::8000 failed: port is already allocated`）は正確だが、初見だと「このプロジェクトが壊れている」ように見える。

`"${BACKEND_PORT:-8000}:8000"` にして、既定は変えずに上書きだけ効くようにした。`NEXT_PUBLIC_API_URL` も同じ変数を参照させないと、ポートを変えたときにフロントだけ古い URL を見に行く。

---

## 9. `NEXT_PUBLIC_` は実行時に渡しても効かない

frontend のコンテナに `NEXT_PUBLIC_API_URL` を environment で渡しているのに、ブラウザ側のコードが既定値を見ていた。

`NEXT_PUBLIC_` 接頭辞の変数は**ビルド時にバンドルへ文字列として焼き込まれる**。実行時の環境変数はサーバ側のコードにしか届かない。Dockerfile 側で `ARG` として受け取り、compose の `build.args` にも同じ値を書く必要がある。

「環境変数だから実行時に差し替えられる」という思い込みが通用しない箇所で、ADR-005 で扱った二重 URL 問題の続きでもある。

---

## 10. `next/font/google` はビルドを外部依存にする

`create-next-app` の雛形は Google Fonts を読み込む。便利だが、**ビルド時にフォントを取りに行く**ため、Docker のビルドや将来のオフライン CI が外部到達性に依存する。

見た目のためにビルドの安定性を落とす取引になっていないか、と考えて外した。社内向けツールなので、システムフォントで困らない。日本語フォントだけは明示しないと環境ごとに行間がずれるので、そこは `--font-sans` に並べている。

---

## 11. 「押せそうに見える」と「押せる」がずれていた

一覧のカードに `hover:border-slate-400` を付けて、ホバーで枠線が変わるようにした。ところが実際にリンクになっていたのは **Skill 名のテキストだけ**で、カードの余白や説明文をクリックしても何も起きなかった。自分でテストしたときは名前を正確にクリックしていたので気づかず、指摘されて初めて分かった。

**見た目が「ここは押せる」と約束している範囲と、実際の当たり判定を一致させる**必要がある。ホバー効果を付けた時点で、その領域全体がクリック可能であるべきだった。

修正で詰まったのは、カード全体を `<Link>` で包めないこと。カードの中にタグへのリンクがあり、**`<a>` の入れ子は HTML として不正**で、ブラウザがパース時に構造を壊す。使ったのは stretched link パターン:

```jsx
<li className="relative ...">
  <Link href={...} className="... after:absolute after:inset-0 after:content-['']">{name}</Link>
  ...
  <Link href={`/?tag=...`} className="relative z-10 ...">#{tag}</Link>
```

名前リンクの `::after` を擬似要素としてカード全面に広げ、タグ側を `relative z-10` で上に載せる。`z-10` を忘れるとタグを押しても詳細へ飛ぶ。

**学び**: 自分でテストするとき、開発者は「正しい場所」を狙って押してしまう。**UI の検証は「一番押しそうな場所」を押すべきで、「動くと分かっている場所」を押しても検証にならない。** 自動テストでも同じで、要素をセレクタで取得して `click()` すると、当たり判定の問題は永久に見つからない。

## 迷って決めきれなかったこと（残った宿題）

- **並行アップロードの版番号採番**: `(skill_id, version)` の UNIQUE 制約で衝突は検出できるが、検出後のリトライは実装していない。同名 Skill を同時にアップロードすると片方が 500 になる。実運用の頻度を見てから決めたい
- **孤児ファイルの掃除**: ストレージ保存後・DB コミット前に落ちると ZIP だけが残る。害はないが溜まる。掃除の仕組みは作っていない
- **`SKILL.md` の大文字小文字**: 現状は完全一致で判定している。`skill.md` を弾くのが親切なのか不親切なのかは、実際に使う人の反応を見ないと分からない
